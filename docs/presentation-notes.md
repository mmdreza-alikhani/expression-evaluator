## ۱) پیام اصلی ارائه (یک جمله)

**«الگوریتم در هر سه زبان یکی است؛ تفاوت واقعی در نحوهٔ مدیریت حافظه، خطا و هزینهٔ runtime است.»**

این جمله را در ابتدا و انتها بگو. کل ارائه باید همین را ثابت کند.

---

## ۲) ساختار پیشنهادی ۸–۱۰ دقیقه‌ای

### اسلاید ۱ — مسئله (۱ دقیقه)

بگو:

> عبارت‌های ریاضی به شکل infix نوشته می‌شوند؛ مثل `3 + 4 * (2 - 1)`. انسان اولویت عملگرها را می‌فهمد، ولی ماشین اگر ساده از چپ به راست بخواند، جواب غلط می‌دهد. دو راه حل هست: درخت نحو (AST) یا تبدیل به postfix و ارزیابی با استک. من راه دوم را انتخاب کردم چون بدون بازگشت، در یک گذر و با زمان O(n) کار می‌کند.

نکتهٔ کلیدی: **postfix ابهام را حذف می‌کند**؛ در `3 4 2 1 - * +` هیچ اولویتی باقی نمی‌ماند.

### اسلاید ۲ — الگوریتم مشترک (۲ دقیقه)

روی تخته یا اسلاید، چهار مرحله را بکش:

```
ورودی → توکن‌ساز → Shunting-yard → postfix → ارزیابی با استک → نتیجه
```

برای هر مرحله یک جمله:

1. **توکن‌ساز:** عدد، عملگر و پرانتز را جدا می‌کند؛ فاصله‌ها را نادیده می‌گیرد. متغیر `expect_operand` می‌گوید الان operand انتظار داریم یا operator؛ همین متغیر منهای یکانی را تشخیص می‌دهد.
2. **Shunting-yard:** اولویت `* / = 2`، `+ - = 1`، `(` = 0 و منهای یکانی `u = 3`. تا وقتی اولویت بالای استک بزرگ‌تر یا مساوی است، pop می‌کنیم (چپ‌انجمنی). پرانتزها با استک تطبیق داده می‌شوند.
3. **Postfix:** خروجی بدون ابهام؛ مثلاً `3 4 2 1 - * +`.
4. **ارزیابی:** هر عدد push؛ هر عملگر دو مورد آخر را pop می‌کند (b سپس a) و نتیجه را push می‌کند. `u` یک مورد را pop و علامتش را برمی‌گرداند. تقسیم بر صفر چک می‌شود.

مثال دقیق `3 + 4 * (2 - 1)` را گام‌به‌گام نشان بده؛ خروجی `3 4 2 1 - * +` و نتیجه `7`.

### اسلاید ۳ — کد سه زبان (۲ دقیقه)

اینجا نقطهٔ اصلی «تفاوت» است. یک قطعه کد کوتاه از هر زبان نشان بده و بگو:

| مفهوم | Python | Go | C11 |
|---|---|---|---|
| استک | `list` با `append/pop` | `[]float64` و `[]byte` داخل `numStack/opStack` | آرایهٔ پویا با `items/len/cap` و `realloc` |
| خطا | `raise ExprError` | `return value, error` | `return -1` + `err[256]` |
| عدد | `float()` | `strconv.ParseFloat` | `strtod` + مسیر سریع اختیاری |
| حافظه | GC | GC | دستی: `evaluator_free` |

فایل‌ها و توابع کلیدی:

- Python: `python/evaluator.py` — `tokenize` (خط ۳۴)، `to_postfix` (۸۰)، `eval_postfix` (۱۳۴)
- Go: `go/main.go` — `tokenize` (۸۷)، `toPostfix` (۱۵۶)، `evalPostfix` (۲۳۳)
- C: `c/evaluator.c` — `tokenize` (۱۹۸)، `to_postfix` (۳۱۱)، `eval_postfix` (۴۱۴)، `evaluator_free` (۵۳۰)

جملهٔ مهم:

> منطق یکی است؛ در Python استک فقط یک لیست است، در Go یک slice با متدهای push/pop، و در C یک ساختار با ظرفیت و `realloc`. خطا هم در Python استثناست، در Go مقدار بازگشتی، و در C کد خطا.

### اسلاید ۴ — تست و صحت (۱ دقیقه)

- یک فایل تست مشترک: `tests/cases.txt` با ۶۴ کیس.
- هر سه زبان: **۶۴/۶۴ پاس**.
- خروجی هر سه یکسان است؛ مثلاً `2 * (-3)` → `2 3 u *` و `-6`.
- C با AddressSanitizer هم ۶۴/۶۴ پاس و بدون خطای حافظه؛ بیلد Debug CRT بدون نشتی.
- تست‌ها شامل: تقدم، چپ‌انجمنی، پرانتز تودرتو، اعشار، منهای یکانی، خطاها.

بگو:

> چون هر سه از یک فایل تست و یک قالب خروجی (`%.10g`) استفاده می‌کنند، «یکسان بودن نتیجه» قابل اثبات است، نه ادعا.

### اسلاید ۵ — بنچمارک (۲ دقیقه)

جدول ۱ میلیون توکن:

| زبان | میانگین | حافظه |
|---|---:|---:|
| Python | 1020 ms | 301 MB |
| Go | 29.2 ms | 80 MB |
| C | 24.0 ms | 52 MB |

نکات:

- C سریع‌ترین و کم‌مصرف‌ترین است.
- Go تقریباً هم‌سرعت C است، ولی ۱٫۵ برابر حافظه می‌خواهد.
- Python حدود ۴۲ برابر کندتر از C است؛ دلیلش تفسیر، شیء‌بودن اعداد و هزینهٔ نوع‌های پویاست.
- اعداد بین اجراها نوسان دارند (بار سیستم، GC)؛ این‌ها خروجی واقعی همین ماشین است.

**نکتهٔ شفافیت (مهم):** C یک مسیر سریع برای اعداد کوتاه دارد (`mantissa / 10^frac` به‌جای `strtod`). اگر همین کد را با `strtod` خالص کامپایل کنیم، ۱ میلیون توکن **۵۸٫۱ms** می‌شود؛ یعنی Go از C سریع‌تر می‌شود. پس بگو:

> «C با پیاده‌سازی بهینه‌شده سریع‌ترین است؛ نه اینکه C ذاتاً همیشه سریع‌ترین باشد.»

این جمله نشان می‌دهد تحلیل‌گر هستی، نه فقط طرفدار یک زبان.

### اسلاید ۶ — نتیجه‌گیری (۱ دقیقه)

- **Python:** نمونه‌سازی سریع، آموزش، ابزار داخلی، ورودی کوچک.
- **Go:** بهترین تعادل؛ سرعت نزدیک C + ایمنی حافظه + توسعهٔ سریع‌تر. برای اکثر سرویس‌ها.
- **C:** سیستم‌های نهفته، پردازش سیگنال، کتابخانه‌های هسته‌ای، جایی که هر میلی‌ثانیه/مگابایت مهم است.

جملهٔ پایانی:

> «برای این مسئله C سریع‌ترین است، Go متعادل‌ترین، و Python ساده‌ترین. انتخاب درست به محدودیت پروژه بستگی دارد، نه به سرعت خالی.»

## ۳) نسخهٔ کوتاه ۳ دقیقه‌ای

1. مسئله: infix مبهم است؛ postfix + استک ابهام را حذف می‌کند. (۳۰ ثانیه)
2. الگوریتم: tokenize → shunting-yard → postfix → stack eval. مثال `3+4*(2-1)=7`. (۶۰ ثانیه)
3. تفاوت: یک الگوریتم، سه پیاده‌سازی از استک/خطا/حافظه؛ Python list+exception، Go slice+error، C realloc+error code. (۶۰ ثانیه)
4. نتیجه: ۶۴/۶۴ تست، C 24ms / Go 29ms / Python 1020ms؛ C سریع ولی دستی، Go متعادل، Python ساده. (۳۰ ثانیه)

## ۵) بانک سؤال و جواب

**۱. چرا AST استفاده نکردی؟**
> برای این مسئله AST اضافه‌کاری است. postfix + استک همان نتیجه را با کد کمتر، بدون بازگشت و O(n) می‌دهد. AST وقتی بهتر است که متغیر، تابع یا چند بار ارزیابی داشته باشیم.

**۲. چرا منهای یکانی را `u` گذاشتی؟**
> چون `-` دودویی و یکانی رفتار متفاوت دارند. با یک نشانهٔ جدا (`u`) و اولویت ۳، هم `-3+4` هم `2*(-3)` هم `--5` درست می‌شوند.

**۳. چرا `3 4` خطا می‌دهد؟**
> چون بعد از عدد اول، `expect_operand` false است؛ عدد دوم بدون عملگر می‌آید و «missing operator» می‌شود.

**۴. چرا خروجی هر سه یکی است؟**
> الگوریتم یکسان، تست مشترک ۶۴ کیس، و قالب عددی یکسان (`%.10g` در C، `FormatFloat` در Go، `.10g` در Python). همه با تلورانس 1e-9 مقایسه می‌شوند.

**۵. چرا Python این‌قدر کند است؟**
> هر توکن یک تاپل و هر عدد یک شیء `float` است؛ حلقه در مفسر اجرا می‌شود و هر عملیات بررسی نوع دارد. برای ۱ میلیون توکن حدود ۱ ثانیه یعنی ~۱µs به‌ازای هر توکن.

**۶. چرا Go از C کندتر است؟**
> GC، تخصیص‌های پویا، bounds check و runtime. اختلاف فقط ~۲۰٪ است، ولی ایمنی حافظه و سرعت توسعه را می‌خرد.

**۷. چرا C حافظهٔ کمتری می‌خواهد؟**
> ساختارهای پیوسته و فشرده، بدون runtime و GC. در عوض مدیریت حافظه دستی است و باید `free` کند.

**۸. مقایسه منصفانه است؟**
> الگوریتم یکی است، ولی C یک بهینه‌سازی محلی برای پارس عدد دارد. بدون آن، C در ۱M توکن ۵۸ms می‌شود و Go سریع‌تر است. برای مقایسهٔ کاملاً هم‌سطح، باید همان بهینه‌سازی را در Go/Python هم گذاشت یا هر دو نسخه را گزارش کرد.

**۹. چرا `valgrind` استفاده نکردی؟**
> پروژه روی ویندوز اجرا شد و valgrind در دسترس نبود؛ به‌جایش AddressSanitizer مایکروسافت و Debug CRT برای نشتی استفاده شد. روی لینوکس `make asan` یا valgrind هم قابل اجراست.

**۱۰. چرا `3.` و `1..2` خطا هستند؟**
> طبق قرارداد پروژه، نقطهٔ اعشار باید حداقل یک رقم بعد از خود داشته باشد. `.5` معتبر است.

**۱۱. پیچیدگی زمانی/مکانی چیست؟**
> هر مرحله O(n)؛ کل O(n) زمان و O(n) حافظه. هر توکن یک‌بار push و حداکثر یک‌بار pop می‌شود.

**۱۲. اگر عبارت خیلی بزرگ باشد چه می‌شود؟**
> الگوریتم خطی است؛ محدودیت اصلی حافظه است. C کمترین مصرف را دارد، Go وسط، Python بیشترین. برای ورودی‌های چند میلیون توکن، C/Go مناسب‌ترند.
